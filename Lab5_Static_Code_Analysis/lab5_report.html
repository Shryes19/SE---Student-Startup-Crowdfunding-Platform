Reflection Questions

1. What is static code analysis, and how does it differ from dynamic testing?

Static code analysis inspects source code without executing it. Tools parse the abstract syntax tree (or bytecode) and apply rule sets to flag potential problems before a single line runs. Dynamic testing, by contrast, executes the program and observes runtime behaviour — it can catch issues that only arise with specific inputs (null pointer dereferences, race conditions, runtime exceptions) but misses problems that only appear in code paths never exercised by the test suite. Static analysis is faster and catches a different, complementary category of bugs: naming convention violations, unused variables, insecure API usage, and formatting inconsistencies are all invisible to a running program but instantly visible to a static analyser.

2. Which tool found the most critical issue, and why is it important?

Bandit found the most critical issue: the use of MD5 as a security hash (B324, Severity: High). MD5 is cryptographically broken — collisions can be generated quickly, so if the hash were ever used to protect sensitive data (e.g., passwords, integrity checks), an attacker could forge matching values. Even though in this program the hash is used only as a short display ID, flagging it forces developers to be explicit about intent by adding usedforsecurity=False. This guards against a future maintainer copy-pasting the same pattern into a security-critical context.

3. How did fixing naming and style issues (Pylint / Flake8) improve the code?

Renaming camelCase functions like addMovie to snake_case add_movie aligns the code with PEP 8 and Python's standard library, making it immediately readable to any Python developer. Adding docstrings turns implicit assumptions into explicit contracts — a reader knows what each function expects and returns without reading the body. Replacing for i in range(len(titles)) with enumerate is both more Pythonic and less error-prone (no off-by-one risk). Consistent blank lines (E302) reduce visual noise and help editors and linters agree on where functions begin and end. Collectively these fixes reduced future cognitive load and eliminated several entire classes of subtle bugs.

4. How does static analysis contribute to code quality and maintainability over time?

Static analysis works best as a gate in the CI/CD pipeline. Every pull request runs the same checks, so quality standards are enforced uniformly rather than depending on individual reviewer knowledge. Over time this accumulates significant benefits: the codebase stays consistently readable as team membership changes, security regressions are caught before reaching production, and technical debt is addressed incrementally rather than in expensive rewrites. Pylint's scoring also gives teams a measurable, objective proxy for code health — a score drifting from 9.8 to 8.5 is a visible signal that standards are slipping and prompts corrective action before the problem becomes large.
